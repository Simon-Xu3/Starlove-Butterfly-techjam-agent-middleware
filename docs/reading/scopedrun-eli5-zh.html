第 1 步：先抓住核心

把 Agent 想成一个临时进房间的小机器人

以前：机器人进房间后，主要依赖 UI 和提示词告诉它“不要碰某些东西”。

ScopedRun：门卫在开门之前检查它的通行证。通过后，房间里只出现被批准的一个只读文件夹；没有被批准的文件夹，房间里根本不存在。

目标
允许 orders-incident 时，Agent 可以读它。
目标
没允许 payments-incident 时，Agent 连看都看不到它。
第 2 步：什么变了

从最基础的版本，到现在的最新提交

基础版本：Agent Launchpad

它已经是一个能跑的 Agent 平台：

  • 网页里创建 Agent、聊天、继续同一对话
  • Fastify 服务处理请求和异步 Run
  • 持久保存 Agent 工作区和 Codex 对话
  • 用 Docker / Colima / Podman 跑一次 Agent 工作

但它是单用户 demo：没有“谁是谁”、没有资源授权、没有审计收据。

当前实现：ScopedRun

原有平台已经新增一条“资源入场检查线”：

  • 识别 demo 用户是谁
  • 确认这个用户是否拥有该 Agent
  • 确认用户当前有资格把这个资源委托给本次 Run
  • 只把批准的目录只读挂载进容器
  • 留下不泄露敏感信息的决定收据

当前证据：确定性测试覆盖身份、owner、Entitlement、Run Delegation、路径、Receipt、Advisor 和 UI；真实容器 Kill Test 证明只挂载明确委托的只读目录，其他目录不存在，宿主文件保持不变。最终演示仍需要有效 Ark 凭据和额度来展示真实模型答案。

第 3 步：为什么不只做一个按钮？

因为“叫 Agent 不要看”不是真的限制

Agent 能运行命令、找目录、读文件。网页不显示某个资源，或 prompt 写着“不要读它”，都只是提醒，不是门锁。

办法为什么不够
网页选择器直接调用 API 或走别的执行路径时，网页可以被绕过。
提示词规则模型遵守提示词不等于操作系统拒绝文件访问。
事后日志日志只能告诉你“发生过什么”，不能阻止已经发生的读取。
ScopedRun在 Agent 启动前改变它实际看得见的文件系统。

这就是这个 hackathon 项目真正要展示的 middleware：不是给 Agent 加一句建议，而是在控制层和容器边界加一道可验证的门。

第 4 步：你作为用户到底怎样用它

“有权使用”不等于“这次自动交给 Agent”

用户权限是上限；本次任务的明确批准，才是 Agent 这次真正看得见的范围。

1
写任务。例如：“分析订单服务昨晚为什么失败。”
2
看可选资料包。系统只列出你有资格委托的安全资料名称和简介，不显示真实文件路径或内容。
3
可选：获得建议。Advisor 可以根据任务和这些安全简介建议 orders-incident；建议不是授权，Agent 不能自动接受它。
4
你明确批准。你可以选一个资料包、移除建议，或一个也不选。选一个才是 Capsule Run；不选就是旧的普通 Run。
5
服务器再检查一次。确认你仍有权限、你拥有当前 Agent、资料安全、容器支持，然后才启动。
6
这次 Run 结束，委托结束。容器只读看到你批准的一个资料包；下一次 Run 要重新选择和检查。
我们想要
人可以控制本次 Agent 的资料范围；AI 可以帮助找资料，但不能替人开门。
我们不想要
“Alice 有订单资料权限，所以 Alice 的 Agent 自动拿到所有订单资料”。这不是最小权限。

MVP 的刻意限制：一次只批准一个目录资料包，而且只读。写权限、多资料包、自动扩大范围都不做。

第 5 步：它具体怎样工作

允许时：7 个小动作

1
用户在网页选择一个资源 ID，例如 orders-incident。用户永远不发送电脑上的真实路径。
2
服务器从 X-Demo-Session 请求头识别 demo 用户，例如 user-a。这只是 demo 身份，不是生产登录。
3
服务器确认：这个用户拥有这台 Agent。
4
服务器确认：当前用户拥有有效的 Principal Resource Entitlement，而且这次请求明确创建了一个 Run Delegation。Entitlement 是上限，不是 Agent 的长期可见范围。
5
服务器从自己的 Resource Registry 找到资源，检查真实路径没有 ..、软链接逃逸或越界。
6
服务器生成一张不可修改的“挂载计划”：把该目录只读放到容器内 /resources/orders-incident。
7
容器启动。Agent 读取被允许的资料；服务器保存一张安全的 Decision Receipt（决定收据）。

拒绝时：最重要的是“不启动”

例子：user-a 的 Agent 想读没有授权的 payments-incident。

服务器创建一个状态为 denied 的 Run，返回安全的 403 和一张拒绝收据。
必须能证明：
Runner 调用次数 = 0。
容器没有启动。
payments-incident 没有出现在挂载清单里。

这比“Agent 读了以后再提醒它不该读”强得多：拒绝是在执行前发生的。

第 5 步：几个名字不要混

6 个最重要的积木

Human Principal
这次 demo 里正在操作的人，例如 user-a。
Agent ownership
“这台 Agent 属于谁”。别人不能拿走它操作。
Protected Resource
可被严格控制的服务器目录，例如事故资料包。
Principal Resource Entitlement
“这个人最多可以委托哪些目录”的服务器端上限。
Run Delegation
这个人本次明确选择的零或一个目录；Run 结束即结束。
Decision Receipt
一张安全的小收据：谁、哪个 Agent、选了什么、允许还是拒绝、Runner 是否启动。

还有一个关键名词：ValidatedRunMountPlan。它是服务器签发给容器的只读挂载计划；浏览器和 Agent 都不能自己写这张计划。

第 6 步：团队怎样完成它

先证明门锁能锁，再完成产品

这是两天 hackathon。团队把最危险的验证提前：先证明容器只读挂载与 namespace 缺失，再并行完成控制层、持久化、UI、文档和演示。

第一个不可跳过的 Gate（前两小时）：真实容器 Kill Test
  • 允许的 orders-incident 可以读取
  • 未授权的 payments-incident 在容器中不存在
  • 尝试写入允许目录会失败（只读）
  • 宿主机文件的 hash 和修改时间没有变化
  • Runner 不接受调用方随便传来的路径或挂载参数

如果这五项无法证明，团队就应该调整方案，而不是把 UI 或 prompt 当成“安全”。

第 7 步：诚实的边界

我们在证明什么，又没有证明什么

我们要证明

  • 未授权的服务器目录不会进入这一次容器 Run 的文件系统。
  • 拒绝发生在 Runner 启动前。
  • 允许的目录以只读方式挂载。
  • 每次决定都有不泄密的证据收据。

我们不声称

  • 生产级 OAuth、RBAC 或多租户隔离。
  • 拦截所有网络、MCP、HTTP 或任何工具调用。
  • 撤销后立即卸载一个已经在运行的容器。
  • 让模型忘记它先前合法读过的内容。

“撤销”只影响未来的新 Run。旧 Run、旧对话和历史收据会保留；这是产品有意说清楚的限制。
